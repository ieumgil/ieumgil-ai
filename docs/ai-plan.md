# AI 설계 v3 (확정: LLM이 읽고 · 판단하고 · 계획하고 · 풀어준다)

> 2026-11-10 확정. v2(① 판단 엔진 · ② 일정 설계 루프 · ③ 추가 질문)를 공공데이터 조사 결과(`docs/data/tour-api-fields.md`)에 맞춰 다시 짰다.
> 이 문서가 AI 관련 기준이다. CLAUDE.md 원칙 1·2번, `docs/planning.md`의 AI·데이터 부분은 이 문서를 따른다.

## 왜 LLM이 메인인가

- 데이터: 한국관광공사 무장애 여행정보 API(KorWithService2)로 강릉·속초·동해 관광지·문화시설 182곳을 받아, 관광지가 아닌 곳을 빼고 **152곳**을 쓴다(① 읽기 완료, 아래 결과).
  무장애 정보는 "출입구까지 경사로가 설치되어 있음(완만함)", "장애인 전용 화장실 있음(3.1기념공원 주차장)" 같은 **짧은 문장으로만** 있다.
  정해진 틀이 없어 코드로는 가능/불가를 가를 수 없고, 기존 사이트는 문장을 그대로 보여주고 판단을 여행자에게 넘긴다.
- 이음길은 **LLM이 이 문장을 읽고, 이 사람 기준으로 판단하고, 일정으로 엮고, 현장에서 쓸 말로 풀어준다.**
  LLM을 빼면 152곳 데이터는 판단에 쓸 수 없다 → 중간평가 25점 항목("생성형 AI가 문제 해결에 실질적으로 기여")에 정면으로 답한다.
- 중간평가 배점: 문제 정의·필요성 20 / **AI 활용 적정성 및 실현 가능성 25** / 진행률·팀 활동 성실도 20 / 혁신성·창의성 15 / 지속가능성 20.
  공고 의무 결과물: "핵심 기능 1개 이상 작동(예: 사용자 질의 → 생성형 AI 응답 → 작동)". 제출한 계획서: "생성형 AI는 관광지 접근성 정보 분석과 개인별 추천 사유 설명에 활용".
- 코드는 **계산과 검사**만 한다. 판단과 말은 LLM이 하고, LLM 출력은 모두 정해진 JSON 틀로 받아 코드가 검사한 뒤 화면에 그린다.

## 원칙 (CLAUDE.md 1·2번)

1. **LLM이 읽고·판단하고·계획하고·풀어준다. 코드는 계산과 검사만 강제한다.**
   - LLM 출력은 전부 JSON 스키마로 받는다(ajv 검사). 형식이 틀리면 1회 재시도, 그래도 틀리면 그 결과를 버린다.
   - 근거 id가 없거나 넘겨준 문장 밖을 가리키는 판단·문장은 버린다. 입력에 없는 시설·시간·거리를 쓰지 않는다.
   - **시각은 LLM이 쓰지 않는다.** 도착·출발 시각은 코드가 이동시간 + 체류 + 여유로 계산한다.
   - 안전 하한(코드가 강제): 필수 조건이 '불가'면 부적합, '모름'이면 '확인 필요'(적합 금지), '부분가능'이면 최소 '주의'.
   - LLM이 실패하면(시간 초과, 형식 오류, 호출 한도) 규칙 일정 1개를 보여준다. 시연이 멈추면 안 된다.
2. **'모름'은 숨기지 않고 확인할 방법을 준다.** (이전 원칙 "'정보 없음' 금지"를 대체)
   - 접근성 값은 `가능 | 부분가능 | 불가 | 모름`. 빈칸은 반드시 '모름'으로 두고 지어내지 않는다.
   - '모름'에는 물어볼 질문(`ask`)이 반드시 있어야 한다. 장소에는 공식 전화번호가 반드시 있어야 한다(API 97% 보유).
   - 빌드 검사: '모름'인데 질문이 없거나, 부분가능인데 메모가 없거나, 전화번호가 없으면 실패.
   - 값마다 출처 등급을 단다: `ai`(LLM이 관광공사 문장을 읽고 정리) / `human`(사람이 전화·현장으로 확인). 화면에 함께 표시한다.

## LLM이 하는 4가지 일

| 일 | 언제 | 입력 | 출력(JSON) | 코드가 하는 일 |
|---|---|---|---|---|
| ① 읽기 | 미리(스크립트, 152곳 완료) | 장소별 API 문장(무장애·소개·반복·개요) | 접근성 10항목 값 + 메모 + 근거 + '모름'이면 질문, 운영시간 정리, 도착 후 동선 초안 | 스키마·근거 id 검사, 반복·모델 간 일치율 측정 |
| ② 판단 | 요청할 때 | ① 결과 + 원문 문장 + 사용자 조건(유형·추가 질문 답) | 장소마다 적합/주의/부적합/확인 필요 + 이유 + 근거 + 확신도 | 안전 하한 적용, 3회 판단 비교로 확신도 |
| ③ 계획 | 요청할 때 | ② 적합·주의 장소 우선 + 확인 필요(표시해서), 이동시간 표, 운영시간, 화장실 위치 | **성격이 다른 일정 2~3안**(장소·순서·체류·쉬는 곳·이유·주의·확인 질문) | 시각 계산, 운영시간·하루 범위 검사, 위반이면 수정 요청, 통과한 안만 노출 |
| ④ 풀어주기 | 미리 만들고 요청할 때 다듬기 | ①의 동선 초안, ② 이유, ③ 안 | 도착 후 동선, 출발 전 확인할 것(질문 + 전화), 대안 설명 | 대안 장소는 코드가 좌표·판단으로 고르고 LLM은 이유만 |

LLM 호출은 요청당 약 6~8회: 추가 질문 1 · ② 판단 3(후보를 한 호출에 묶고 3번 반복) · ③ 계획 1(2~3안을 한 번에) · 수정 0~2(걸린 안만) · 평가 1.

### ① 읽기 — 문장 → 판단할 수 있는 데이터 (미리)

입력은 API 문장 그대로다. 문장마다 근거 id를 붙여 넘긴다(`route-1`, `restroom-1`, `info-화장실-1` …).

```json
{
  "placeId": "GN05",
  "access": {
    "slope": { "value": "가능", "note": "완만한 경사로", "evidence": ["route-1"] },
    "accessible_toilet": { "value": "부분가능", "note": "주차장 쪽에만 있음, 관람 구역과 떨어짐", "evidence": ["restroom-1"] },
    "elevator": { "value": "모름", "ask": "2층 이상 관람 공간이 있나요? 있다면 엘리베이터로 갈 수 있나요?" }
  },
  "hours": { "summer": { "open": "09:00", "close": "18:00", "last_entry": "17:00" }, "winter": null, "closed_weekdays": ["월"], "evidence": ["usetime-1", "restdate-1"] },
  "onSite": { "text": "장애인 주차는 잔디광장(2대) → 경사로로 주출입구 → 화장실은 주차장 쪽", "evidence": ["parking-1", "route-1", "restroom-1"] }
}
```

- 빈칸은 반드시 '모름'. 문장이 애매하면 '부분가능'이 아니라 '모름' + 질문.
- 운영시간은 LLM이 문장에서 `open/close/last_entry`로 정리하고, 코드가 형식(HH:MM, open < close)을 검사한다. 하절기·동절기 구분이 없으면 같은 값을 쓰고 표시한다.
- **사람 판정은 기본으로 하지 않는다(11/10 결정).** 확인이 필요한 항목은 사용자에게 질문 + 공식 전화번호로 넘긴다. 사람이 확인한 값이 생기면(`data/eval/human.json`, 양식은 `scripts/ai/human-template.ts`) 등급 `human`으로 덮어쓴다.
  사람이 판정한 값은 등급 `human`으로 LLM 값을 덮어쓴다.

### ② 판단 — 이 사람에게 맞는가 (요청할 때)

- 입력: 코드가 먼저 거른 후보(지역·휴무·필수 조건 '불가' 제외, 최대 20곳), ① 결과, 원문 문장, 사용자 조건(유형, 걸을 수 있는 거리, 추가 질문 답).
- 출력: `{ placeId, verdict: "적합"|"주의"|"부적합"|"확인 필요", reasons[1~3], evidence[], confidence }`.
  예: "주의. 경사로는 완만해서 보호자가 밀면 들어갈 수 있지만, 장애인 화장실이 주차장 쪽에만 있어서 관람 전에 들르는 게 좋아요."
- 안전 하한(코드): 필수 항목 '불가' → 부적합, '모름' → 확인 필요(① 질문 + 전화번호 첨부), '부분가능' → 최소 주의. LLM은 더 보수적으로만 바꿀 수 있다.
- 자기 일관성: 같은 판단을 3번 돌린다. 셋 다 같으면 확신 높음, 2:1이면 보수적인 쪽(부적합 > 확인 필요 > 주의 > 적합) + 확신 보통, 셋 다 다르면 확인 필요 + 확신 낮음.

### ③ 계획 — 하루로 엮기, 여러 안 (요청할 때)

한 번 호출로 **방향이 다른 일정 2~3안**을 받는다. 프롬프트에서 안마다 전략을 지정한다(예: A 여유롭게 · B 바다 중심 · C 비 와도 괜찮게 실내 위주). 취향과 후보에 따라 전략은 코드가 고른다.

```json
{
  "options": [
    {
      "id": "A",
      "strategy": "여유",
      "title": "여유롭게 바다 보기",
      "summary": "걷는 거리를 줄이고 쉬는 시간을 넉넉히 넣었어요.",
      "days": [
        { "date": "2026-11-21", "stops": [
          { "placeId": "GN12", "stayMin": 60, "why": "데크가 평평해 휠체어로 바다 가까이 갈 수 있어요", "evidence": ["route-1"], "restAfter": true },
          { "placeId": "GN03", "stayMin": 45, "why": "실내라 쉬어 가기 좋고 장애인 화장실이 입구 옆이에요", "evidence": ["restroom-1"] }
        ] }
      ],
      "cautions": [{ "placeId": "GN12", "text": "해변 데크 끝은 모래라 진입 불가", "evidence": ["handicapetc-1"] }],
      "checkBeforeGo": [{ "placeId": "GN03", "question": "2층 전시실에 엘리베이터가 있나요?" }]
    }
  ]
}
```

| LLM이 채우는 값 | 코드가 하는 일 |
|---|---|
| 장소 선택·순서·날짜 배분, 머무는 시간, 쉬는 곳 | 장소 id가 후보에 있는지, ② 판단이 부적합이 아닌지. 확인 필요는 허용하되 안마다 개수를 세어 표시(적합·주의가 충분하면 그쪽 우선) |
| 안 제목·요약, 장소별 이유, 주의, 확인 질문 | 시각 계산(이동시간 표 + 체류 + 유형별 여유 + 승하차 여유 + 12~14시 점심 60분), 운영시간·하루 범위 검사 |
| | `stayMin`이 장소 체류 범위 밖이면 범위 안으로 맞춤 |
| | 형식 오류·검사 위반 → 위반 내용을 돌려줘 **걸린 안만** 다시 요청(최대 2회), 끝까지 못 통과한 안은 뺀다 |

- 평가 역할 LLM: 안마다 피로도·여유·취향 1~5점 + "화장실 있는 곳 사이 간격", "쉬는 시간"을 점검. 2점 이하가 있으면 1회 수정.
  안끼리 장소가 절반 넘게 겹치면 다시 만들게 한다.
- 후보가 적으면 안 1개만 만들고 "조건에 맞는 곳이 적어 한 가지 안만 만들었어요"를 보여준다.
- 이동시간 표(카카오 다중 목적지, 날짜마다 ≤6회)는 루프 전에 한 번 만들어 넣는다. 함수 호출(도구)은 쓰지 않는다.

### ④ 풀어주기 — 현장에서 쓸 말

- **도착 후 동선**: ①에서 장소별로 미리 만든 초안을, 요청할 때 사용자 유형에 맞춰 한 줄로 다듬는다.
- **출발 전 확인할 것**: '확인 필요' 항목의 질문 + 공식 전화번호 버튼.
- **대안**: 빠진 장소가 있으면 근처(좌표) 적합 장소를 **코드가** 고르고, LLM이 이유를 쓴다. "○○는 모래사장이라 어려워요. 3km 떨어진 ○○ 데크 산책로는 어떠세요?"

### ⑤ 추가 질문 (v2 ③ 유지)

- 4단계 입력을 보고 LLM이 애매한 점만 0~3개 질문. 답의 효과는 정해진 `TravelerTraits` 항목으로만 받고, 모르는 키·값은 버린다.

```ts
interface TravelerTraits {
  wheelchairKind?: "manual" | "electric";
  assisted?: boolean;              // 밀어주거나 부축하는 동행자
  restEveryMin?: 30 | 60 | 90 | null;
  standingLimitMin?: 10 | 30 | 60 | null;
  strollerKind?: "light" | "large";
  toiletUrgent?: boolean;
}
```

## ① 읽기 결과 (11/10, 152곳)

- 대상: API 182곳 중 관광지가 아닌 곳·전화번호 없는 곳 30곳(화장실, 문화원, 공연장, 숙박형 리조트, 주민시설 등)을 빼고 **152곳**(강릉 101 · 속초 30 · 동해 21).
- 모델: `gemini-3.5-flash-lite`로 4곳씩 37회. `gemini-3.8-flash`는 503(수요 과다)이 이어지고 무료 한도가 하루 약 20회라 이번엔 쓰지 않았다(사람 40곳 기준으로 두 모델 정확도 비교는 평가 단계에서).
- 교훈: 근거 id `enum`·중첩 배열 길이 제한을 모델 스키마에 넣으면 400("too many states") → 모델에는 가벼운 스키마, 받은 답은 엄격한 스키마로 검사(`llm.ts`의 `check`).
- 근거 없이 채운 값 0건(코드가 '모름'으로 바꾼 값 0). '모름' 58%(889/1520). 운영시간 143곳 정리(상시 개방 81, 시각 62), 모름 9곳. 도착 후 동선 77곳.
- **야외 시설 엘리베이터 규칙(코드)**: 관광공사 분류가 자연관광(NA)·도시공원(VE03)이면 '층이 없는 야외 시설'로 보고 엘리베이터를 '가능'으로 둔다(근거: `class-1` 분류 문단, 59곳). 조건표의 엘리베이터는 층이 있는 시설에만 해당하기 때문.

| 보행 불편 어르신(300m) | 0 | 0 | 152 | 0 |

**결정(11/10): '확인 필요' 장소도 일정에 넣고 분명히 표시한다.** API에 노면·경사·거리가 거의 없어 휠체어·어르신은 안전 하한만으로 대부분 '확인 필요'가 된다.
- ③ 계획 후보는 적합·주의를 먼저, 모자라면 확인 필요로 채운다. 데이터상 '불가'(부적합)는 여전히 뺀다.
- 확인 필요 장소는 카드에 "출발 전 확인" 질문 + 공식 전화번호를 크게 붙이고, 안 비교 화면에 "확인 필요 ○곳"을 보여준다. 평가자는 확인 필요가 많은 안을 낮게 본다.
- **사람 판정은 하지 않는다(11/10).** 휠체어·어르신 일정에 '확인 필요'가 많이 나오는 것을 받아들이고, 질문과 전화번호로 사용자가 확인하게 한다.

## 테스트와 평가

- **단위 테스트(CI, 가짜 LLM)**
  - 근거 없는 판단·문장은 버려진다
  - 필수 '모름' → 확인 필요, '불가' → 부적합, '부분가능' → 적합 불가
  - LLM이 어떤 안을 내도 검사 통과한 안만 화면에 나간다, 시각은 코드 계산값만 쓴다
  - 걸린 안만 다시 요청한다, LLM 실패 시 규칙 일정 1개
  - 추가 질문의 모르는 키는 버려진다
  - 장소 검사: '모름'에 질문, 부분가능에 메모, 전화번호
- **AI 평가(`scripts/eval-ai.ts`, 수동)**
  - 사람 정답 없이 자동으로 잰다(11/10 결정). 정확도가 아니라 **일관성** 지표라는 점을 그대로 밝힌다.
  - ① 읽기: 근거 없이 채운 값 0건(완료) · 같은 모델로 40곳 다시 읽어 항목별 일치율 · Flash-Lite vs Flash 40곳 일치율
  - ② 판단: 3회 판단 일치율(확신도 높음/보통/낮음 분포), 안전 하한으로 바뀐 비율
  - ③ 계획: 규칙 일정 대비 위반 수·평가 점수, 안 사이 겹침 비율
  - 결과는 `docs/eval/`에 날짜별 기록 → README·발표 자료
