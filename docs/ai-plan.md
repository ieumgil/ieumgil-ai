> 2026-11-10 claude.ai 대화에서 확정. 이전 후보 22개 목록은 이 문서로 대체한다.

## 왜 바꾸나

- 공고 결과물 의무: "핵심 기능 1개 이상 작동 (예: 사용자 질의 → 생성형 AI 응답 → 작동)"
- 중간평가 25점 항목: "생성형 AI가 문제 해결에 **실질적으로 기여**하며, 활용 도구·데이터가 구체적인가"
- 제출한 개발 계획서: "생성형 AI는 관광지 **접근성 정보 분석**과 개인별 추천 사유 설명에 활용"
- 기존 원칙("판정은 규칙, LLM은 설명만")은 계획서보다 AI 역할이 좁고, AI를 빼도 돌아가는 구조였다.

## 새 원칙 (CLAUDE.md 1번을 이것으로 교체)

1. **AI가 판단하고 계획한다. 코드는 '불가' 데이터와 계산만 강제한다.**
   - LLM: 장소가 이 사람에게 맞는지 판단(①), 일정 작성·수정(②), 추가 질문 생성(③), 이유 설명.
   - 코드: 필수 조건이 데이터상 '불가'인 장소 제외, 휴무 제외, 이동·체류·운영시간 **계산**, 일정 위반 검사, LLM 출력 검증.
   - LLM은 우리 데이터와 근거 문서에 없는 시설·시간·거리를 만들지 않는다. 근거 문서 id가 없는 판단은 버린다.
   - LLM이 실패하면(시간 초과, 형식 오류, 호출 한도) 규칙만으로 만든 일정을 보여준다. 시연이 멈추면 안 된다.

## 전체 흐름

```
[입력 4단계] → [③ AI 추가 질문 0~3개] → [만드는 중 화면] → [결과 /trip/[id]]
                                          │
   서버 POST /api/plan (진행 상황을 스트리밍으로 보냄)
     1. 후보 거르기 (코드)       필수 조건 '불가', 휴무, 지역
     2. 근거 모으기 (RAG)        장소별 근거 문서 + 기준 문서
     3. ① 장소 판단 (LLM×3)      적합/주의/부적합 + 이유 + 근거 + 확신도
     4. 출력 검증 (코드)         근거 id 존재, '부분가능' 필수 항목은 최소 '주의'
     5. 이동시간 표 (카카오)     날짜마다 6회 이하
     6. ② 일정 초안 (LLM)        선택·날짜 배분·순서·체류·쉬는 곳
     7. 시간표 계산 + 검사 (코드) 운영시간, 하루 범위, 점심, 이동
     8. 위반 → LLM 수정          최대 2회
     9. 일정 평가 (LLM 평가자)   피로도·여유·취향 점수, 기준 미달이면 수정 1회
    10. 실패 시 규칙 일정        점수 상위 N곳 + 순서 전수 탐색
```

LLM 호출은 요청당 6~8회(질문 1, 판단 3, 초안 1, 수정 0~2, 평가 1). 설명 문장은 판단·평가 응답에 같이 받아 호출을 늘리지 않는다.

## ① AI 접근성 판단 엔진

**입력**: 사용자 조건 요약(개인정보 없음), 후보 장소 목록, 장소별 근거 문서, 관련 기준 문서

**출력 (장소마다)**
```ts
interface PlaceJudgment {
  placeId: string;
  verdict: "적합" | "주의" | "부적합";
  reasons: string[];          // 1~3개, 이 사람 기준
  evidence: string[];         // 근거 문서 id. 넘겨준 목록 밖이면 무효
  onSite?: string;            // 도착 후 한 줄 동선 팁 (근거 있을 때만)
}
```

**자기 일관성**: 같은 판단을 3번(온도 조금씩 다르게) 시킨다.
- 3번 일치 → 확신 높음
- 2:1 → 더 보수적인 쪽(부적합 > 주의 > 적합)을 쓰고 확신 보통
- 셋 다 다름 → '주의' + 확신 낮음 + "방문 전 전화 확인" 표시

**코드가 하는 검증**
- `evidence`가 비었거나 넘겨준 문서 밖 → 그 판단 버림 → 규칙 판단(`conditions.ts`)으로 대체
- 필수 항목이 '부분가능'인데 '적합' → '주의'로 내림
- 형식 오류 → 1회 재시도 후 규칙 판단

### RAG 자료 (`data/docs/`)

| 폴더 | 내용 | 누가 모으나 |
|---|---|---|
| `data/docs/places/{id}.md` | 장소별: 관광공사 무장애 정보 원문 발췌, 시설 안내문, 안내도 설명, 사진 설명, 전화 확인 메모. 문단마다 id(`GN01-03`)와 출처 URL | 조사 담당 |
| `data/docs/standards/*.md` | 편의시설 설치 기준 요약(경사로 기울기, 화장실 규격, 단차 등), 유형별 이동 가이드(수동·전동휠체어, 유모차, 고령자) | 조사 담당 |

- 장소가 수십 곳이라 장소 문서는 **id로 바로 가져온다**(벡터 검색 불필요).
- 기준 문서는 문단 단위로 나눠 빌드 시점에 임베딩(`data/embeddings.json`)하고, 사용자 조건·접근성 항목으로 검색해 상위 몇 개만 넣는다. 벡터 DB 없이 메모리에서 코사인 유사도.
- 문서도 `places.json`처럼 검사 스크립트로 형식(문단 id, 출처 URL)을 확인한다.

## ② AI 일정 설계 루프

**LLM이 정하는 것**: 어떤 장소를, 며칠째에, 어떤 순서로, 몇 분 머물지, 어디서 쉬는지
**코드가 정하는 것**: 도착·출발 시각 계산(이동시간 표 + 체류 + 승하차 여유 + 점심 60분), 위반 검사

```ts
interface PlanDraft {
  days: { date: string; stops: { placeId: string; stayMin: number; restAfter?: boolean }[] }[];
  rationale: string;          // 전체 구성 이유 1~2문장
}
interface Violation { day: number; placeId?: string; kind: "운영시간" | "하루범위" | "점심" | "체류범위" | "판단부적합"; message: string }
```

- LLM은 시간 산수를 하지 않는다. 초안 → `computeTimeline()` → `checkPlan()` → 위반 메시지를 그대로 LLM에 돌려줘 수정시킨다.
- `stayMin`은 장소의 `stay_min~stay_max` 밖이면 코드가 범위 안으로 맞춘다.
- 일정 평가자(별도 프롬프트): 피로도, 시간 여유, 취향 반영을 1~5점 + 한 줄 이유. 하나라도 2점 이하이면 개선 지시와 함께 1회 수정.
- 이동시간 표는 루프 전에 한 번 만들어 넣는다(카카오 호출 한도). 함수 호출(도구)은 쓰지 않는다.

## ③ AI 추가 질문

- 4단계 입력을 보고 LLM이 **애매한 점만** 0~3개 질문을 만든다. 없으면 바로 다음 화면.
- 질문 문장은 LLM이 만들지만, **답의 효과는 정해진 항목으로만** 받는다. LLM이 새 조건을 만들 수 없다.

```ts
// PlanInput에 추가
interface TravelerTraits {
  wheelchairKind?: "manual" | "electric";
  assisted?: boolean;              // 밀어주거나 부축하는 동행자
  restEveryMin?: 30 | 60 | 90 | null;
  standingLimitMin?: 10 | 30 | 60 | null;
  strollerKind?: "light" | "large";
  toiletUrgent?: boolean;          // 화장실을 자주 가야 함
}
interface AiQuestion {
  id: string;
  text: string;                    // LLM 문장
  options: { label: string; set: Partial<TravelerTraits> }[];   // 2~4개
}
```

- 서버가 `options[].set`을 스키마로 검증한다. 모르는 키·값이면 그 선택지는 버린다.
- 화면은 기존 `choices.tsx` 선택 카드를 그대로 쓴다. 자연어 입력 없음.
- 답한 traits는 ① 판단과 ② 일정 프롬프트에 함께 들어간다.

## 테스트와 평가

- **단위 테스트(CI)**: LLM을 가짜로 바꿔 고정 응답을 넣는다. 지켜야 할 것:
  - 근거 없는 판단은 버려지고 규칙 판단으로 바뀐다
  - '부분가능' 필수 항목은 '적합'이 될 수 없다
  - LLM이 어떤 초안을 내도 `checkPlan()` 통과한 일정만 화면에 나간다
  - LLM 실패 시 규칙 일정이 나온다
  - ③ 선택지의 모르는 키는 버려진다
- **AI 평가(`scripts/eval-ai.ts`, 수동 실행)**: 시나리오 30개에 사람이 정답(장소별 적합/주의/부적합)을 단다.
  - 판단 일치율, 확신도별 정답률
  - 규칙만 쓴 일정 vs AI 일정: 위반 수, 평가자 점수, 사용자 테스트 선호
  - 결과는 `docs/eval/`에 날짜별 기록 → README와 발표 자료에 사용
