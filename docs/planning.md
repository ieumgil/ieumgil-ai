## 사용자 유형과 필수 조건

세 유형은 막히는 지점이 달라서 유형마다 필수 조건 세트를 따로 적용한다. 여러 유형을 고르면 각 항목에서 가장 엄격한 값을 쓴다. 예를 들어 고령자 + 유모차를 고르면 걸을 수 있는 거리와 수유실을 모두 본다.

| 항목 | 휠체어 | 유모차 | 보행 불편 고령자 |
| --- | --- | --- | --- |
| 계단·단차 없는 진입로 | 필수 | 주의 표시(짧은 단차는 들어서 통과) | 주의 표시(손잡이 있으면 가능) |
| 엘리베이터(층이 있는 시설) | 필수 | 필수 | 선호 |
| 경사로 기울기 | 필수(급경사 불가) | 선호 | 주의 표시(긴 오르막) |
| 노면(모래·자갈·흙길) | 필수(포장·덱크 구간 있어야 함) | 선호 | 주의 표시(넘어짐 위험) |
| 장애인 화장실 | 필수 | — | 선호 |
| 기저귀 교환대·수유실 | — | 선호 | — |
| 장애인 전용 주차구역 | 필수(자가용 + 표지 차량일 때) | 이용 대상 아님 | 장애 등록 시만(입력 선택) |
| 주차장에서 입구까지 거리 | 주의 표시 | 주의 표시 | 필수(입력한 거리 이하) |
| 관람 동선 길이 | — | 선호 | 필수(입력한 거리 이하) |
| 휴식 공간(벤치·쉬터) | — | 선호 | 선호 |
| 휠체어·유모차 대여 | 선호 | 선호 | 선호 |

- **필수**: 하나라도 어기면 후보에서 빠지고 '불가 + 대안' 목록으로 간다.
- **선호**: 추천 점수에만 더해진다.
- **주의 표시**: 일정에는 남기고 장소 카드에 경고 문구를 붙인다.
- **고령자 입력값**: 한 번에 걸을 수 있는 거리(100m / 300m / 500m / 제한 없음). 주차장→입구, 관람 동선과 비교한다.
- 사용자는 유형을 고른 뒤 자동으로 켜진 조건을 하나씩 끄거나 더할 수 있다.

## 사용자 흐름과 화면

입력은 설문조사처럼 4단계로 나누고, 한 화면에는 질문 하나만 둔다. 결과 화면은 지도와 루트를 함께 보여준다.

**시작 화면**: 서비스 한 줄 소개, '시작하기', '예시 루트 바로 보기'. 예시 루트는 미리 만든 공유 링크라 심사위원이 입력 없이 결과를 볼 수 있다.

**입력 4단계**

1. **언제, 어디서**: 달력에서 가는 날·오는 날(당일\~2박 3일). 영동 도착 지점, 이동수단(자가용·렌터카 / 택시), 자가용이면 장애인 표지 차량 여부. 첫날 시작 시각, 마지막 날 마치는 시각과 떠나는 곳(기본값: 도착 지점). 1박 이상이면 숙소 지역(강릉·속초·동해·미정).
2. **누구와**: 휠체어 / 보행 불편 고령자 / 유모차, 중복 선택.
3. **꼭 필요한 조건**: 유형별 필수 조건이 미리 켜져 있고 끄거나 더할 수 있다. 장애인 전용 주차는 1단계에서 표지 차량을 고른 경우에만 나온다. 고령자를 고르면 한 번에 걸을 수 있는 거리를 고른다.
4. **좋아하는 곳**: 바다·해변 / 자연·산책 / 역사·문화 / 전시·박물관 / 시장·먹거리 / 전망·체험 중 복수 선택. 일정 밀도(여유롭게 / 보통 / 많이). 꼭 가고 싶은 곳 검색(선택). 입력 화면에 "이름·연락처는 받지 않고, 고른 조건은 일정 계산에만 써요"를 표시한다.

**결과 화면 구성**

- **날짜별 탭**: 1박 이상이면 일차별 탭. 탭마다 판정, 지도, 루트가 바뀜다.
- **판정 배지**: "약 5\~6시간 · 여유 있어요"처럼 여유 / 빠듯 / 부족 중 하나.
- **지도**: 방문 순서 번호 마커, 자동차 경로선, 출발·도착 지점. "휠체어 안전 경로가 아닌 일반 차량 경로" 안내를 붙인다.
- **루트 카드(장소별)**: 사진, 이름, 권장 체류 범위, 조건 체크, 주의 문구, 주차·입구 메모, 근거 펼치기(출처·확인일), '출발 전 전화로 확인' 버튼.
- **구간 이동**: 카드 사이에 "차량 약 25분 · 14km".
- **점심·휴식 블록**: 일정이 12\~14시에 걸리면 60분 빈 블록. 음식점은 추천하지 않는다.
- **불가 장소와 대안**: 취향에 맞지만 조건 때문에 빠진 유명 관광지를 이유와 함께 보여주고 대안을 추천한다.
- **AI 브리핑**: 여행 전체 요약 1개 + 일차별 브리핑(루트 요약, 장소별 포인트, 내 유형의 주의사항, 준비물).
- **편집**: 장소 빼기, 추가, 순서 바꾸기(드래그와 위·아래 버튼), 다른 날로 옮기기. 바꾸면 판정과 경로를 다시 계산한다.
- **공유**: 링크 복사, 일차별 요약 이미지 저장.
- **오류 화면**: 경로를 못 불러옴(직선거리 추정치로 대체), 조건에 맞는 곳 없음(완화 제안), AI 설명 실패(기본 브리핑).

**화면 배치**: PC는 왼쪽 지도 + 오른쪽 루트 카드. 모바일은 위쪽 지도 + 아래쪽 카드 목록. 공유 링크로 열면 편집 버튼 대신 "내 일정으로 복사"를 보여준다.

## 일정 생성 로직

11월 10일부터 일정은 AI가 판단하고 설계하며, 코드는 '불가' 데이터 제외와 시간 계산·위반 검사만 강제한다. 모든 단계는 서버(`POST /api/plan`)에서 돌고 진행 상황을 스트리밍으로 보낸다. 상세 설계(출력 형식, 검증 규칙, 호출 횟수)는 `docs/ai-plan.md`가 기준이다.

1. **후보 거르기(코드)**: 필수 조건이 데이터상 '불가'인 곳, 그 날 휴무인 곳, 지역 밖을 뺀다.
2. **근거 모으기(RAG)**: 장소별 근거 문서(`data/docs/places/{id}.md`)는 id로 가져오고, 기준 문서(`data/docs/standards/`)는 임베딩 검색으로 상위 몇 개만 넣는다.
3. **① 장소 판단(LLM × 3)**: 적합 / 주의 / 부적합 + 이유 + 근거 문서 id. 세 번 판단해 일치하면 확신 높음, 2:1이면 보수적인 쪽, 셋 다 다르면 '주의' + 방문 전 전화 확인.
4. **출력 검증(코드)**: 근거 id가 없거나 넘겨준 목록 밖이면 그 판단을 버리고 규칙 판단으로 대체한다. 필수 항목이 '부분가능'이면 '적합'을 '주의'로 내린다.
5. **이동시간 표(카카오)**: 다중 목적지 길찾기, 날짜마다 6회 이하.
6. **② 일정 초안(LLM)**: 장소 선택, 날짜 배분, 순서, 체류 시간, 쉬는 곳. LLM은 시간 산수를 하지 않는다.
7. **시간표 계산 + 검사(코드)**: 이동 + 체류 + 승하차 여유 + 점심 60분으로 시각을 계산하고 운영시간·하루 범위·점심·체류 범위를 검사한다.
8. **위반 → LLM 수정**: 위반 메시지를 그대로 돌려줘 최대 2회 고치게 한다.
9. **일정 평가(LLM 평가자)**: 피로도·여유·취향 반영 1\~5점. 하나라도 2점 이하이면 1회 더 고친다.
10. **실패 시 규칙 일정**: LLM이 실패하거나 끝까지 위반이 남으면 아래 '규칙 일정'으로 만든다. 검사를 통과한 일정만 화면에 나간다.
11. **경로선**: 정해진 순서로 '다중 경유지 길찾기'를 1회 호출한다.

LLM 호출은 요청당 6\~8회(추가 질문 1, 판단 3, 초안 1, 수정 0\~2, 평가 1)이고, 카카오 길찾기는 하루치 일정마다 최대 7회다.

### 규칙 일정 (LLM 실패 시 대체 경로)

LLM 없이도 시연이 멈추지 않도록 아래 규칙 일정은 그대로 유지한다. 개수·배분·시간 규칙은 AI 일정의 검사 기준으로도 쓴다.

1. **후보 걸러내기**: 영동권 전체 장소에서 선택한 유형의 필수 조건을 어기는 곳, 그 날 휴무인 곳을 뺀다. 장애인 전용 주차 조건은 자가용 + 장애인 표지 차량일 때만 켠다. 빠진 곳 중 취향에 맞는 곳은 '불가 + 대안' 목록으로 보낸다.
2. **점수 매기기**: 취향 일치 + 선호 조건 충족 개수 + 도착 지점과의 거리. 꼭 가고 싶은 곳은 항상 포함한다.
3. **개수 정하기**: 반나절 2\~3곳, 하루 3\~5곳. 일정 밀도(여유롭게 / 보통 / 많이)가 하한·중간·상한을 고른다. 여러 날이면 날마다 같은 규칙을 적용하고, 조건을 통과한 장소가 모자라면 상한을 자동으로 낮추고 안내한다.
4. **날짜별 배분(1박 이상)**: 장소를 지역(강릉·속초·동해) 단위로 묶어 날짜에 나눈다. 첫날은 도착 지점 쪽, 다음 날부터는 숙소 지역 쪽 묶음부터 채운다. 같은 장소는 한 번만 들어간다. 중간 날은 숙소 09:30 출발 \~ 18:00 도착을 기본값으로 두고, 마지막 날은 떠나는 곳(기본값: 도착 지점)에서 끝난다. 숙소가 '미정'이면 첫날 마지막 장소 근처를 숙소로 가정하고 그렇게 표시한다.
5. **이동시간 표 받기**: 점수 상위 장소와 도착 지점 사이의 차량 이동시간을 카카오 '다중 목적지 길찾기'로 받는다(날짜마다, 출발점마다 1회, 최대 6회).
6. **순서 정하기**: 장소가 5곳 이하라 가능한 순서를 모두(최대 120가지) 계산한다. 비용 = 총 이동시간 + 운영시간 위반 벌점. 가장 낮은 순서를 고른다.
7. **시간 범위 계산**: 총 이동시간 + 장소별 권장 체류 범위의 합 + 유형별 여유시간. 여유시간은 휠체어·고령자 선택 시 체류 범위에 20\~30%를 더하는 것을 초기값으로 두고 조정한다. 여기에 휠체어를 고르면 장소마다 승하차 여유시간을, 일정이 12\~14시에 걸리면 점심·휴식 60분 블록을 더한다. 승하차 여유시간 값은 조사나 테스트로 정한다.
8. **판정**: 범위 최대값 ≤ 여행 시간 → 여유. 최소값 ≤ 여행 시간 < 최대값 → 빠듯. 최소값 > 여행 시간 → 부족(점수가 가장 낮은 1곳을 뺀 안을 함께 제시). 1박 이상이면 날짜마다 따로 판정한다.
9. **운영시간 검사**: 늦은 쪽 도착 예상 시각이 입장 마감을 넘으면 경고하고, 이른 쪽도 넘으면 순서에서 뺀다. 시각 단위가 아니라 휴무일·마감 같은 큰 제약만 보며, 여행 날짜에 맞춰 하절기·동절기 운영시간과 명절 휴무를 고른다.
10. **경로선**: 정해진 순서로 '다중 경유지 길찾기'를 1회 호출해 지도에 그릴 선과 구간별 시간·거리를 받는다.
11. **완화 제안**: 후보가 부족하면 필수 조건을 하나씩 풀어 보고 늘어나는 장소 수를 계산한다. 결과는 LLM이 한 문장으로 설명한다.

편집(빼기·추가·순서 변경·다른 날로 옮기기) 때는 순서 정하기(AI 초안 포함)를 건너뛰고, 사용자가 정한 순서로 '시간 범위 계산'부터 '경로선'까지만 다시 돌린다. 카카오는 길찾기 결과를 저장해 두고 다시 쓰는 것을 금지하므로, 공유 링크는 장소와 날짜별 순서만 저장하고 열 때 경로를 다시 받는다.

## 데이터 구조

장소 데이터는 저장소 안 `data/places.json` 하나로 둔다. 심사위원이 GitHub에서 검수된 데이터셋을 바로 볼 수 있고, 빌드할 때 형식 검사(JSON Schema)를 돌린다. Supabase에는 공유된 일정만 저장한다.

**장소 항목**

| 필드 | 내용 | 예시 |
| --- | --- | --- |
| id, name\_ko, name\_en | 식별자, 이름(영문명은 관광공사 공식 표기) | gn-ojukheon, 오죽헌 |
| region, category | 강릉 / 속초 / 동해, 취향 카테고리 | 강릉, 역사·문화 |
| lat, lng, address | 좌표와 주소(주차장 좌표가 따로 있으면 parking\_lat/lng) | — |
| hours | 하절기·동절기별 여는 시각·닫는 시각·입장 마감, 휴무 요일, 특정 휴무일(명절 등) | 09:00, 18:00, 17:00, 월 |
| stay\_min, stay\_max | 권장 체류 범위(분) | 40, 70 |
| access.\* | 항목별 값 + 메모 + 출처 URL + 확인일 | 아래 참고 |
| parking\_to\_entrance | 거리(m)와 노면·경사 메모 | 120, 평지 포장로 |
| route\_length | 관람 동선 길이(m)와 메모 | 600, 나무 덱크 |
| photos | URL, 출처 기관, 공공누리 유형, 작가 | 제1유형 |
| alternatives | 불가일 때 추천할 대안 장소 id | — |

**access 항목(조건표와 1:1)**: step\_free\_entrance, elevator, slope, surface, accessible\_toilet, diaper\_nursing, disabled\_parking, rest\_area, rental\_wheelchair, rental\_stroller. 값은 `가능 / 부분가능 / 불가` 중 하나다. 부분가능은 메모가 반드시 있어야 한다(예: "해변 덱크까지 가능, 모래사장 진입 불가").

- 운영 원칙은 '정보 없음' 금지지만, 스키마에는 `미확인` 값을 남겨 두고 빌드 검사에서 하나라도 있으면 실패하게 한다. 조사가 빠진 곳을 자동으로 잡기 위해서다.
- 출처는 항목마다 달아서 관광공사 API, 지자체 페이지, 현장 사진, 전화 확인(날짜·기관)을 구분한다.
- 사진은 공공누리 1유형을 우선 쓴다. 1유형은 출처만 표시하면 자르기·크기 변경이 가능하고, 3·4유형은 변경이 금지된다.

**추가 필드**: `phone`(문의 전화). 루트 카드의 '출발 전 전화로 확인' 버튼에 쓴다. 조사표에도 같은 칸이 있다.

**공유 일정 테이블(Supabase `trips`)**: id(짧은 무작위 문자열), created\_at, 사용자 유형, 켜진 조건, 날짜, 도착 지점, 여행 시간, 이동수단, 숙소 지역, 날짜별 장소 id 순서, AI 추가 질문 답(`TravelerTraits`), 장소 판단 결과 문장, 설계 과정 기록(초안 → 위반 → 수정 → 평가 점수). 이름·연락처 같은 식별정보는 없다. 카카오 경로 결과는 저장하지 않고 열 때 다시 받는다.

## LLM 활용 설계

11월 10일 변경: 기존 원칙("판정은 규칙, LLM은 설명만")은 제출한 개발 계획서("생성형 AI는 관광지 접근성 정보 분석과 개인별 추천 사유 설명에 활용")보다 AI 역할이 좁고, AI를 빼도 돌아가는 구조였다. 이제 AI가 장소를 판단하고 일정을 설계하며, 코드는 안전 하한과 계산을 강제한다. **출력 형식, 검증 규칙, 파일 배치, 작업 순서는 `docs/ai-plan.md`가 기준이다.**

| 쓰임 | 받는 것 | 내놓는 것 | 코드가 강제하는 것 |
| --- | --- | --- | --- |
| ① 장소 판단(LLM × 3) | 조건 요약, 후보 장소, 장소별 근거 문서, 관련 기준 문서 | 적합 / 주의 / 부적합, 이유 1\~3개, 근거 문서 id, 도착 후 팁 | 근거 id 없음 → 버리고 규칙 판단, '부분가능' 필수 항목은 최소 '주의', 2:1이면 보수적인 쪽 |
| ② 일정 초안·수정 | 판단 결과, 이동시간 표, 입력 조건 | 날짜별 장소·순서·체류·쉬는 곳 + 구성 이유 | 시각 계산, 운영시간·하루 범위·점심·체류 범위 검사, 위반이면 최대 2회 수정 |
| ② 일정 평가자 | 완성 일정 | 피로도·여유·취향 1\~5점 + 한 줄 이유 | 2점 이하가 있으면 1회 수정 |
| ③ 추가 질문 | 4단계 입력 | 애매한 점만 질문 0\~3개 + 선택지 2\~4개 | 선택지 효과는 `TravelerTraits` 정해진 항목만, 모르는 키·값은 버림 |
| 데이터 정리 스크립트(개발용) | 관광공사 무장애 설명 문장, 조사 메모 | access 항목별 값 + 근거 문장 초안 | 사람이 검수한 뒤 `places.json`에 반영 |

**원칙**

- **안전 하한은 코드가**: 데이터상 '불가'인 필수 항목, 휴무는 AI 판단과 상관없이 뺀다. AI는 일정을 더 안전한 쪽(부적합, 주의)으로는 바꿀 수 있지만, 규칙이 막은 곳을 살리지 못한다.
- **근거 없는 판단 금지**: 우리 데이터와 근거 문서에 없는 시설·시간·거리를 쓰지 않는다. 근거 문서 id가 없는 판단은 버린다.
- **형식 고정**: JSON으로 받아 스키마 검사 후 쓴다. 형식 오류면 1회 재시도, 그래도 실패하면 규칙 판단·규칙 일정.
- **개인정보 없음**: Gemini 무료 등급은 보낸 내용이 Google 모델 학습에 쓰일 수 있다. `PlanInput` + `TravelerTraits`만 보내고, 자유 입력이 없어 이름·연락처가 들어갈 경로가 없다.
- **실패해도 동작**: 시간 초과, 형식 오류, 호출 한도면 규칙 일정을 보여준다. 시연이 멈추지 않게 하기 위해서다.
- **검증 기록**: CI는 가짜 LLM으로 가드를 검사하고, `scripts/eval-ai.ts`로 시나리오 30개(사람 정답)의 판단 일치율과 규칙 일정 대비 품질을 측정해 `docs/eval/`에 남긴다. 심사에서 AI 활용 적정성의 근거가 된다.
- **제공자 교체 가능**: LLM 호출을 `src/lib/llm.ts` 한 파일로 묶고 모델명은 환경변수로 둔다.

## 기술 스택과 외부 API

Next.js 하나로 화면과 서버 API를 모두 만들고, 외부 서비스는 카카오·Gemini·Supabase 세 가지만 쓴다. 모두 무료 등급 범위다.

| 구분 | 선택 | 쓰임 | 주의할 점 |
| --- | --- | --- | --- |
| 프레임워크 | Next.js(App Router) + TypeScript | 화면 + 서버 API(키 숨김) | — |
| 스타일 | Tailwind CSS | 반응형, 큰 글씨·고대비 | — |

| 이동시간·경로 | 카카오모빌리티 다중 목적지 / 다중 경유지 길찾기 | 순서 계산, 경로선 | 비상업 무료 쿼터. 결과 저장·재사용 금지. 도보 길찾기는 유료 제휴 전용이라 쓰지 않음 |
| LLM | Gemini Flash | 장소 판단, 일정 설계·평가, 추가 질문, 설명, 기준 문서 임베딩 | 무료 등급 호출 한도(요청당 6\~8회), 입력이 학습에 쓰일 수 있음 |

| 이미지 저장 | html-to-image 계열 | 요약 카드 PNG | 지도 캐내스 캐처가 브라우저 보안으로 막힐 수 있음. 1주차에 검증 |

| 데이터 수집 | 관광공사 무장애 여행정보 API | 장소 설명 원문 | 무료, 개발계정 1,000건, 자동승인. 서비스에서는 호출하지 않고 스크립트로만 사용 |

**키 관리**: 카카오 JavaScript 키는 브라우저에 노출되므로 도메인 제한을 건다. 카카오 REST 키, Gemini 키, Supabase 서비스 키는 Vercel 환경변수에만 두고, 저장소에는 `.env.example`만 올린다.

## GitHub·제출 전략

GitHub Organization을 만들고 그 안에 **공개** 저장소 하나를 두는 것을 추천한다. 제출 링크가 팀 이름으로 나가고, Vercel 무료 플랜은 Organization의 공개 저장소는 배포할 수 있다.

| 선택지 | 제출 링크 모양 | 장점 | 주의할 점 |
| --- | --- | --- | --- |
| Organization + 공개 저장소(추천) | github.com/팀이름/저장소 | 팀 프로젝트로 보임, 팀원 권한 관리, 나중에 저장소를 더 만들기 쉬움 | 저장소를 비공개로 바꾸면 Vercel 무료 배포가 막힘. 배포는 본인 커밋으로만 자동 실행 |
| 개인 계정 저장소 | github.com/kjhmoon/저장소 | 설정이 가장 단순, Vercel 제약 없음 | 개인 프로젝트처럼 보임 |

- **첫날 검증**: Organization에 저장소를 만든 직후 빈 Next.js를 Vercel에 배포해 본다. 막히면 개인 계정으로 옮긴다. GitHub는 저장소를 옮겨도 이전 주소를 새 주소로 연결해 준다.
- **오늘부터 공개**: 커밋 기록이 공고의 '진행률·성실도'를 보여 주는 증거다. 작은 단위로 자주 커밋하고, 커밋 메시지는 한국어로 무엇을 바꿨는지 적는다.
- **README 구성**: 한 줄 소개, 배포 URL, 시연 GIF·영상, 문제 정의, 구조 그림(규칙 판정 + AI 설명), 사용자 유형별 조건표, 데이터 출처·검수 방법, 실행 방법, 한계와 면책("일반 차량 경로, 현장 상황과 다를 수 있음"), 팀 소개.
- **저장소에 함께 올릴 것**: `data/places.json`과 데이터 사전, 데이터 정리 스크립트, LLM 테스트 시나리오와 결과, (진행하면) 사용자 테스트 기록, 사진 출처 목록.
- **올리지 않을 것**: API 키, `.env` 파일, 출처 표기 조건이 불분명한 사진 원본.

**엔진 테스트 시나리오**: 아래 10개를 자동 테스트로 만들고, 결과 루트를 조건표와 대조해 필수 조건 위반 0건을 README에 숫자로 남긴다.

## 역할 분담

개발은 공지혁이 전부 맡고, 강환일은 장소 조사와 주간보고를 맡는다. 신청서의 분담(강환일=백엔드)과 달라진 점은 주간보고에 적는다.

| 담당 | 맡는 일 |
| --- | --- |
| 공지혁 | 기획 확정, 화면·서버·데이터 구조 개발, 외부 API 연동, 배포, README |
| 강환일 | 관광지 후보별 무장애 항목 조사(인터넷·전화), 사진과 출처·공공누리 유형 정리, 주간보고 작성(사진 포함), 테스트 참여자 모집 준비 |
| 공동 | 데이터 최종 검수, 기능 테스트, 발표 자료와 결과보고서 |

주간보고에는 "범위를 강릉에서 영동권(강릉·속초·동해)으로 확대"와 실제 역할을 명시한다. 신청서에도 향후 영동권 확대를 적었으므로 계획과 어긋나지 않는다.

## 위험과 미정 사항

가장 큰 위험은 장소 데이터 조사가 늦어지는 것이다. 개발은 강릉 데이터로 먼저 끝까지 돌리고, 속초·동해는 같은 형식으로 채운다.

| 위험 | 대응 |
| --- | --- |
| 조사해도 확인되지 않는 항목이 남음 | 전화 확인. 그래도 안 되면 그 장소를 후보에서 뺀다('정보 없음' 금지 원칙) |
| 지도 이미지 캐처가 막힘 | 장소 위치·순서를 단순한 그림으로 직접 그려 요약 이미지에 넣는다 |
| 카카오 길찾기 호출 오류·한도 | 직선거리 × 보정계수로 임시 이동시간을 보여주고 "추정치"로 표시한다 |
| Gemini 무료 한도 초과(시연 중) | 규칙 기반 기본 브리핑으로 대체. 필요하면 주간보고 지원요청으로 유료 API를 요청 |
| Vercel이 Organization 저장소 배포를 막음 | 개인 계정으로 저장소를 옮긴다 |
| 사용자 테스트 요건(공고상 의무) | 공지를 기다리되, 가족·지인 3\~5명 과제형 테스트 양식을 미리 만들어 둔다 |
| 심사에서 "열린관광 사이트가 있는데?" | 장소 검색이 아니라 유형별 조건 검사 + 자동 루트 + 근거 표시라는 점을 같은 과제 비교 시연으로 보여준다 |
| 유형별로 조건을 통과한 장소가 모자람(특히 2박 3일) | 조사가 끝나면 유형별 통과 장소 수를 센다. 모자란 조합은 하루 상한을 자동으로 낮추고, 그래도 부족하면 그렇다고 안내한다 |
